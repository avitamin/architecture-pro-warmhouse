# Руководство по документации

## Назначение и источники

Репозиторий содержит учебный проект по архитектуре умного дома. Документация должна помогать разбирать и обосновывать решения, а также показывать результат выполнения заданий.

- [Корневой README](../../README.md) определяет требования заданий. Заготовки ответов не являются описанием реализованной системы.
- [Исходные условия проекта](../../docs/project-brief.md) содержат переданное пользователем описание компании, текущей системы, целевой экосистемы и целей бизнеса. Это источник требований, а не свидетельство реализации в репозитории.
- Упомянутый в условиях сдачи шаблон `Project_template` находится в корневом [README.md](../../README.md) под одноимённым заголовком. Заполняй его по мере выполнения заданий в ветке `warmhouse`, сохраняя структуру ответов; отдельную копию шаблона не создавай. Порядок сдачи описан в [AGENTS.md](../../AGENTS.md#порядок-выполнения-и-сдачи).
- Исходники, SQL, манифесты зависимостей и конфигурация подтверждают текущее поведение и устройство приложения. Работоспособность подтверждается отдельно выполненными проверками.
- Согласованные с пользователем решения определяют целевую архитектуру. Предложения и альтернативы до выбора пользователя помечаются как рассматриваемые варианты.
- [Состояние проекта](../project-state.md) — датированный обзор для навигации, а не замена исходникам. Перед использованием сверяй относящиеся к задаче сведения.

Если источники расходятся, явно разделяй требование, реализацию и результат проверки. Не устраняй расхождение предположением.

## Архитектурные решения и обучение

Не заполняй задания готовой целевой архитектурой до обсуждения с пользователем. После выбора кратко фиксируй контекст, принятое решение, рассмотренные альтернативы, основания выбора и последствия в соответствующем разделе проектной документации.

Отделяй текущее устройство системы от целевого, а требования задания — от дополнительных предложений. Сохраняй формат результата, который требует задание: если нужны диаграммы, не заменяй их текстом.

Изменяемые сведения храни в документе состояния. Обновляй только затронутые разделы, дату их сверки и источники при существенном изменении состояния; формальное обновление после каждого действия не требуется.

## Проверки

Проверки выбираются по изменённой части проекта. Следующие команды описывают способы проверки и сами по себе не означают, что проверки уже выполнены.

| Изменение | Проверка | Граница результата |
| --- | --- | --- |
| Документация | Проверить относительные ссылки, Markdown, соответствие утверждений источникам и наличие ссылок из документа-владельца | Не подтверждает запуск приложения |
| Go-код | Из `apps/smart_home`: `go test ./...` и `go vet ./...` | При отсутствии тестов успешная команда не доказывает поведение API |
| Docker Compose | Из `apps`: `docker compose config`; если используется отдельный исполняемый файл — `docker-compose config` | Подтверждает корректность конфигурации, но не готовность сервисов |
| Интеграция | После подготовки окружения и запуска сервисов выполнить `Create Sensor`, затем повторить `Get All Sensors` из [Postman-коллекции](../../apps/smarthome-api.postman_collection.json) | Отдельно проверить ответы API и получение изменяющихся значений температуры согласно заданию |

При изменении контракта API сверяй маршруты, модели, клиент внешнего сервиса и соответствующие запросы Postman. При описании БД сверяй SQL и обращения к данным; при описании запуска — Compose, Dockerfile, скрипт запуска и переменные окружения в коде.

В отчёте указывай фактически выполненные команды и результаты. Используй `PASS`, `FAIL`, `NOT RUN` или `BLOCKED`, поясняя причину последних двух статусов. Разделяй статическое изучение, проверки Go, валидацию Compose и запуск интеграционных сценариев.
