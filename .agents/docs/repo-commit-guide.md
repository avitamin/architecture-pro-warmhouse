# Repo Commit Guide

## Source Priority

Факт: это личный учебный репозиторий; постоянные ориентиры находятся в [AGENTS.md](../../AGENTS.md), требования заданий — в [README.md](../../README.md).

Приоритет для commit workflow: явный запрос пользователя, применимые инструкции AGENTS.md, это руководство, остальные документы проекта, текущая ветка и история коммитов. Фактический staged diff определяет содержание коммита; запрос и история не заменяют просмотр изменений.

Факт: пользователь указал хранить служебные руководства только в `.agents/`. Этот guide находится в `.agents/docs/`; отдельную копию в `docs/` не создавать.

## Commit Message Format

Факт: при инициализации руководства история содержала только `Initial commit`; CONTRIBUTING и отдельного стандарта сообщений нет. Этого недостаточно для вывода об устойчивом формате.

По умолчанию: короткая английская тема с глаголом действия и конкретным предметом изменения, без точки в конце. Не вводить Conventional Commits без отдельного решения пользователя. Для простого изменения достаточно темы; тело нужно, если оно помогает объяснить причины или ограничения.

Примеры:

```text
Add project guidance for architecture learning
Document current system architecture
Implement temperature API
```

## Issue Key Rules

Факт: в изученных требованиях и истории нет обязательных issue keys или связи с трекером задач.

По умолчанию: issue key не нужен; не выводить его из названия учебного задания. Если пользователь явно дал ключ, использовать его по его указаниям.

Проверка совпадения issue key в ветке и теме здесь не применяется: такого контракта и конфигурации gate в репозитории нет. Не создавать искусственный ключ или конфигурацию проверки ради шаблона навыка. Проверять реальную ветку, staged diff и тему средствами Git, описанными ниже.

## Branch Policy

Факт: при инициализации руководства рабочая ветка — `main`, upstream — `origin/main`; задокументированного запрета на прямой коммит в main нет. Это не утверждение о настройках защиты удалённой ветки.

По умолчанию: выполнять запрошенный коммит в текущей именованной ветке; отдельную ветку для небольшой документационной задачи автоматически не создавать. При detached HEAD сначала определить целевую ветку с пользователем.

При запросе push использовать настроенный upstream текущей ветки. Если upstream отсутствует или неоднозначен, уточнить назначение. При отклонении push из-за защиты ветки или расхождения истории сообщить причину; не менять способ публикации без согласования.

## Staging Policy

По умолчанию: один коммит охватывает одну связанную задачу. Сначала прочитать изменения, затем добавить точные пути через `git add -- <paths>` и проверить `git diff --cached`. Служебные документы входят в задачу, если их создание или изменение согласовано.

По умолчанию: локальные IDE-файлы не включать в коммит инструкций. Уже подготовленные изменения вне текущей задачи не считать автоматически разрешёнными к включению.

## Validation Policy

Порядок перед коммитом:

1. Проверить `git branch --show-current`, `git status --short` и upstream через `git branch -vv`.
2. Сверить выбранные файлы и тему с фактическим изменением.
3. Выполнить подходящие проверки из [руководства по документации](repo-documentation-guide.md). Для изменений только Markdown достаточно проверки ссылок, содержания, разметки и `git diff --cached --check`; сборка Go и запуск контейнеров не требуются.
4. После staging проверить `git diff --cached --name-status` и полный `git diff --cached`: только согласованные файлы, без случайных изменений.
5. После commit проверить `git log -1 --format=fuller`, `git show --stat --oneline HEAD` и `git status --short`.
6. После push подтвердить, что удалённая целевая ветка указывает на отправленный коммит; не считать локальный commit доказательством публикации.

## Missing Facts And Defaults

Факт: отдельные требования к релизам, именованию рабочих веток и обязательным проверкам CI в изученных файлах не обнаружены.

Указанные выше правила по умолчанию выбраны для текущего личного учебного проекта, а не выведены из единственного коммита. При появлении собственных соглашений обновить этот guide. Глобальные инструкции остаются действующими и здесь не дублируются.
