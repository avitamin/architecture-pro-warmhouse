## Требования задания и открытые решения

Корневой README требует анализ монолита, выделение доменов и контекстов, диаграммы C4 и ER, выбор и документирование API, завершение контейнерного окружения и разработку MVP микросервисов.

Исходное описание компании сохранено в [условиях проекта](../docs/project-brief.md). Условие описывает управление отоплением и опрос датчиков сервером; исходники учебного монолита подтверждают API управления датчиками и HTTP-клиент температуры, но не реализацию команд отопления. При анализе As-Is эти источники следует различать.

Бизнес-цель MVP в условиях перечисляет отопление, освещение, наблюдение и ворота, а задание 6 в README требует сервисы телеметрии и устройств. Начальная декомпозиция на устройства, телеметрию, пользователей и сценарии расширена отдельным сервисом видеонаблюдения для независимого масштабирования. Отопление, освещение и ворота остаются возможностями общей модели оборудования; интерпретация бизнес-цели и основания выбора зафиксированы в [доменном документе](../docs/to-be-domain-notes.md#декомпозиция-на-микросервисы-задание-2).

Для задания с окружением требуется реализовать `temperature-api` с портом по умолчанию 8081, добавить настройки PostgreSQL и подключить SQL инициализации. Для MVP требуется создать сервисы телеметрии и устройств на разных ООП-языках и интегрировать их с монолитом; брокер сообщений указан как необязательный.

Согласованы пять предметных областей с отдельными моделями данных и отдельно масштабируемый шлюз интеграций — шесть логических сервисов. Каждый сервис управляет своими данными; прямое чтение и изменение чужих таблиц исключены. Связи между моделями используют идентификаторы и межсервисные контракты. Для MVP выбрана одна общая БД PostgreSQL на общем экземпляре, с отдельными схемами и ролями сервисов. Вариант отдельных экземпляров отменён пользователем с учётом небольшой команды. PostgreSQL сохраняет технологию монолита; отдельное хранилище телеметрии не добавляется. Принимаются общая нагрузка и зависимость от доступности БД; схемы не изолируют отказ экземпляра. Версия, конфигурация, резервирование, сроки хранения и детальные контракты ещё не выбраны; нагрузочное тестирование не выполнялось. Требования README и принятые архитектурные решения не означают, что эти компоненты уже реализованы.

Выбран отдельный [сервис видеонаблюдения](../docs/to-be-domain-notes.md#видеонаблюдение) с независимым масштабированием. Объём MVP — просмотр в реальном времени без записи и архива; хранилище видеозаписей не добавляется. Принят WebRTC с предпочтительным прямым каналом «камера → браузер» и резервным TURN; ICE/STUN используются для организации связи. TURN — отдельный инфраструктурный контейнер, масштабируемый по медиатрафику, а сервис видео — по нагрузке организации сеансов. Видео не проходит через прикладной сервис, шлюз интеграций или очереди. Камеры регистрируются у устройств; проверка владения использует общий положительный кэш и gRPC. MVP ограничивается совместимыми камерами, конкретные модели не проверены; TURN не заменяет преобразование неподдерживаемого медиапротокола. Приняты расходы на резервный трафик и эксплуатацию. Video управляет сеансом и обращается по gRPC к адаптерам сигнализации шлюза; транспорт определяется существующими возможностями партнёрской камеры, MQTT не обязателен. Продукт и размещение TURN, конкретные сообщения сигнализации, доступ к медиасеансу и отзыв активного просмотра ещё не детализированы. Доступность в любых сетях не гарантируется; реализации и измерений нагрузки нет.

Для измерений и состояний выбран фоновый Pull-опрос независимо от пользовательских просмотров. Телеметрия получает конфигурации через API устройств, ведёт расписание в собственной схеме PostgreSQL, а общий шлюз исполняет задания через адаптеры. Согласованы отдельные очереди опроса и управления и пропуск просроченных опросов. Интервалы и сроки актуальности ещё не выбраны; координация заданий через PostgreSQL и восстановление описаны ниже. Публикация результатов спроектирована через outbox; реализация доставки ещё предстоит. Экран телеметрии читает сохранённые измерения с временными отметками. Для видео выбран WebRTC с резервным TURN.

Для [масштабирования планировщиков](../docs/to-be-domain-notes.md#распределение-планирования-опросов) выбрано общее расписание в схеме телеметрии PostgreSQL. Экземпляры короткими транзакциями с `FOR UPDATE SKIP LOCKED` выбирают разные записи, создают задания в outbox и обновляют следующее время опроса. Relay публикует их в RabbitMQ с устойчивыми идентификаторами при повторах. Сетевые вызовы не выполняются под блокировками планирования. Приняты дополнительная нагрузка и зависимость от БД; точный расчёт времени после задержек и детали синхронизации реестра ещё не определены. Обновлена рабочая Mermaid-схема; реализации, нагрузочных и отказных проверок нет.

Выбран [опрос без накопления и параллельных запросов](../docs/to-be-domain-notes.md#опрос-без-накопления-и-параллельных-запросов) на стороне платформы: одно незавершённое задание на устройство, пропуск новых интервалов при занятости, отсутствие воспроизведения пропущенных опросов после задержки. Учёт задания должен быть долговечным, завершение сверяется по его идентификатору; повторы доставки не должны вызывать параллельное исполнение. После локального таймаута фиксируется «ответ не получен», затем назначается новый опрос с паузой, увеличиваемой при последовательных ошибках до предела. Состояние паузы сохраняется в схеме телеметрии. Принят риск пересечения обработки внутри прибора: платформа адаптируется к существующим протоколам партнёров, требование доработки прошивки для соблюдения нашего срока завершения отклонено. Для поздних ответов и протоколов без корреляции нужны правила адаптера. Политика относится к чтению телеметрии, а не к повтору команд управления; параметры и реализация пока отсутствуют.

Выбраны независимые подписки телеметрии и сценариев на события измерений шлюза через RabbitMQ. Сохранение истории не блокирует обработку события сценарием; экземпляры каждого сервиса распределяют работу внутри своей подписки. Полный отказ планировщика телеметрии всё ещё может остановить новые опросы. Настройки доставки остаются открытыми; политика порядка/свежести и координация состояния правила через короткую транзакцию PostgreSQL согласованы ниже. Принятые механизмы outbox и обработки повторов описаны ниже. Сценарии принимают решение о действии, устройства проверяют команду, шлюз исполняет её. Рабочая Mermaid-схема и выбранные правила находятся в [доменных заметках](../docs/to-be-domain-notes.md#рабочая-схема-шлюза-и-очередей).

Для внутренних заданий и событий [выбран RabbitMQ](../docs/to-be-domain-notes.md#брокер-внутренних-заданий-и-событий): отдельные очереди опроса и управления, exchange измерений и отдельные очереди подписчиков телеметрии и сценариев. Kafka рассмотрена как альтернатива; потребность в журнале для повторного чтения не установлена. Inbox/outbox и идентификаторы сохраняются, однократное физическое выполнение брокером не гарантируется. Версия, типы очередей, лимиты, долговечность и отказоустойчивое развёртывание пока не определены. MQTT устройств и gRPC запросных API выбраны отдельно; прямое видео не использует брокер.

Для [запросных межсервисных API](../docs/to-be-domain-notes.md#запросные-межсервисные-api) выбран gRPC с Protocol Buffers вместо предложенного REST/JSON. Телеметрия получает конфигурации устройств через gRPC; отправитель outbox сценариев передаёт команды устройствам через gRPC с прежним `command_id` при повторах. Ответ подтверждает приём после commit, а не физическое действие. RabbitMQ сохраняется для заданий шлюзу и событий. `.proto`, генерация кода, deadlines, ошибки, аутентификация и балансировка ещё не реализованы. Для пользовательского входа отдельно выбран HTTP/JSON через API Gateway; подробные API-контракты задания 4 остаются незавершёнными.

Для задания 1 согласованы три области текущего монолита: управление устройствами, управление отоплением и мониторинг температуры. Это логические границы ответственности; изоляция контекстов в коде не реализована: учёт и показания объединены в обработчике, модели и таблице датчиков. Управление отоплением подтверждено условием, но отсутствует в учебном коде.

Для команд согласованы стабильный `command_id`, долговечный учёт состояния, исход «результат неизвестен» и запрет безусловного повтора после таймаута. Изменяющие команды одного устройства выполняются последовательно, разных устройств — параллельно; порядок задаёт сервис устройств при принятии команд. Чтения состояния допускаются по возможностям протокола. После неизвестного результата следующая конфликтующая команда автоматически не запускается. Подтверждение очереди не доказывает физического выполнения. Выбраны строка координации устройства, долговечное ожидание в PostgreSQL и выяснение неизвестного исхода без слепого повтора; детали реализации остаются открытыми; детали — в [доменных заметках](../docs/to-be-domain-notes.md#команды-идентификация-результаты-и-повторы).

Для публикации результатов шлюза выбран Transactional Outbox: результат задания и исходящее событие сохраняются одной транзакцией в собственной схеме шлюза в общей БД PostgreSQL. Входное задание опроса подтверждается после commit результата; команды подтверждаются раньше, после commit долговечного приёма в шлюзе. Relay публикует сохранённые события. Повторы доставки допустимы и требуют обработки по `event_id`. Сбой до commit и неопределённость физического выполнения этим не устраняются. Это архитектурное решение; реализация, сроки хранения и ограничения накопления пока не выбраны. Обновлена [рабочая схема](../docs/to-be-domain-notes.md#рабочая-схема-шлюза-и-очередей).

Согласованы inbox/outbox в сценариях и идемпотентный приём команд с outbox в устройствах. Сценарии атомарно сохраняют обработку события конкретной версией правила, его состояние и, при срабатывании, действие с постоянным `command_id`. Для [конкурентной обработки правила](../docs/to-be-domain-notes.md#конкурентная-обработка-одного-правила) выбрана отдельная короткая транзакция с блокировкой строки через `SELECT … FOR UPDATE`; другие обработчики этого правила ждут, разные правила обрабатываются параллельно. Редактирование и отключение согласуются через ту же строку; сетевые вызовы выполняются вне транзакции. Блокировка не сортирует события по `measured_at`, пропуск устаревших измерений сохраняется. Устройства атомарно сохраняют принятую команду, порядок и задание шлюзу; повтор не создаёт новое задание, изменение содержания под тем же идентификатором отклоняется. Решение описано в [доменных заметках](../docs/to-be-domain-notes.md#надёжное-срабатывание-сценариев-и-приём-команд); реализации и проверок конкуренции нет.

Согласована [семантика запуска и восстановления сценариев](../docs/to-be-domain-notes.md#семантика-пороговых-триггеров): первое свежее измерение после включения нового правила создаёт действие один раз, если условие истинно; далее действует переход из ложного в истинное. Изменение условия создаёт новую версию с начальной проверкой по измерению после её активации; старые события не запускают её задним числом. Перезапуск сервиса восстанавливает сохранённое состояние без нового начального действия. Без свежих данных новые действия не создаются, последнее состояние сохраняется с признаком устаревших данных. После восстановления связи сравнивается новое свежее значение с последним принятым состоянием; сам факт восстановления не повторяет команду. Повтор по таймеру и действия по потере связи задаются отдельно.

Для MVP выбрана [политика порядка и свежести](../docs/to-be-domain-notes.md#порядок-и-свежесть-измерений): история сохраняет запоздавшие корректные измерения, управление по текущему состоянию использует только более новые и достаточно свежие данные без ожидания переупорядочивания. Сценарии атомарно проверяют порядок и возраст при обновлении состояния, фиксируют причину пропуска. Принято допущение надёжных часов устройств: источник порядка и возраста — `measured_at` устройства, серверные часы предполагаются согласованными. Это не подтверждённая характеристика подключённого оборудования. Допустимый возраст задаётся для правила; конкретные значения, точность меток и допустимая погрешность ещё не выбраны. Принимается риск пропуска промежуточных переходов. Для событий-фактов, например движения, политика отдельно не согласована.

Области To-Be, их границы и эволюция рабочего варианта сохранены в [docs/to-be-domain-notes.md](../docs/to-be-domain-notes.md) для задания 2. Они не описывают As-Is. Принадлежность устройства пользователю остаётся в контексте устройств; общий шлюз интеграции используется для чтения и команд. Основания исходной декомпозиции — небольшая команда и общая модель устройств; отдельный шлюз рассматривается ради общей протокольной реализации и независимого масштабирования.

Для MVP выбрано [исходящее подключение устройств](../docs/to-be-domain-notes.md#подключение-устройств-к-платформе) по MQTT 5 поверх TLS: соединения обслуживает MQTT-плагин общего RabbitMQ, шлюз отправляет запросы через подписки и обрабатывает коррелированные ответы. Прикладной Pull сохраняется. Домашний хаб и облако производителя в этот путь не включены. Основание выбора — стандартный протокол для партнёров вместо собственного протокола доставки поверх WebSocket; прикладной контракт и достоверный `measured_at` остаются требованиями совместимости. Шлюз проверяет ответы до публикации внутренних событий. Сырые ответы распределяются между экземплярами шлюза общей очередью `devices` по AMQP и сохраняются до ACK. Аутентификация оборудования, QoS, сеансы, сроки сообщений и topic/ACL ещё не определены.

Выбран один общий экземпляр RabbitMQ для MVP с vhost `devices` и `internal`. Шлюз подключается к обоим и проверяет данные на границе; автоматического переноса необработанных сообщений во внутренние подписки нет. Устройства ограничены своими MQTT-каналами, внутренние интерфейсы и управление не публикуются наружу. Заложены независимые настройки подключений и стабильное DNS-имя MQTT-входа для будущего выделения брокера устройств. Принимаются общие ресурсы и область отказа. Лимиты, мониторинг и будущая миграция сеансов/сообщений требуют реализации; кластеризация и HA ещё не выбраны. Изменена документация, развёртывание не выполнялось.

Выбрана [привязка через секрет и кнопку](../docs/to-be-domain-notes.md#привязка-устройства-к-владельцу): пользователь предъявляет код из комплекта, прибор подтверждает конкретную ограниченную по времени попытку кнопкой через аутентифицированный канал. Сервис устройств атомарно закрепляет владельца и отмечает первоначальный секрет использованным; одному прибору соответствует одна активная попытка. Ключ прибора не помещается в QR-код. Домашняя сеть настраивается отдельно по процедуре партнёра. Локальный сброс не снимает облачного владельца; детали передачи, восстановления доступа, учётных данных и ограничений попыток ещё предстоит определить. Это проектное решение, реализации нет.

C4 Context отражает текущую систему по условию: пользователь, монолит и внешние датчики/модули отопления; запросы инициирует сервер. Отличие учебного кода (внешний `temperature-api`, отсутствие команд отопления) явно отмечено в README. БД и внутренние контексты не вынесены на уровень Context.

## Известные ограничения

Для [ожидания команд](../docs/to-be-domain-notes.md#ожидание-команд-в-postgresql-шлюза) выбрана PostgreSQL шлюза. Приёмник идемпотентно сохраняет команду по `command_id`, затем отправляет ACK RabbitMQ; повтор не сбрасывает состояние существующей команды. Фоновый исполнитель подбирает допустимые ожидающие задания и резервирует их через строку координации устройства. После ACK восстановление обеспечивается БД и исполнителем шлюза; брокер уже не отвечает за исполнение. Результат доставляется через outbox, опросы сохраняют ACK после commit результата. Выбран [приоритет ручных команд](../docs/to-be-domain-notes.md#приоритет-ручных-команд): они отменяют старые ожидающие автоматические команды той же возможности; граница отмены хранится долговечно и применяется к поздней доставке. Зарезервированное исполнение не прерывается, неизвестный исход не обходится, новые автоматические действия остаются разрешёнными. Между ручными командами сохраняется порядок принятия. Лимиты накопления, обработка разрывов последовательности и детали выбора ещё требуют реализации. Изменены документы и рабочая схема; реализации нет.

Для [координации изменяющих команд](../docs/to-be-domain-notes.md#координация-команд-через-строку-устройства) выбрана строка на устройство в схеме шлюза PostgreSQL. Короткая блокировка `SELECT … FOR UPDATE` защищает резервирование и завершение; активный `command_id`, владелец, версия и lease сохраняются согласованно с состоянием команды. Сетевой вызов выполняется после commit. Завершение проверяет активную команду и право исполнителя, результат и outbox фиксируются вместе; неизвестный исход не снимает занятость. Это не гарантия отмены старого физического запроса. Ожидающие команды сохраняются в PostgreSQL шлюза; применение ручного приоритета и отмен согласуется через ту же строку. Детали смены исполнителя ещё открыты. Реализация отсутствует.

Для всех сервисов, потребляющих решение о доступе к устройству, выбран [общий внешний кэш положительных результатов авторизации](../docs/to-be-domain-notes.md#кэширование-проверок-доступа-к-устройствам). Источник владения и единственный писатель разрешений — сервис устройств; остальные потребители читают кэш без права изменения или продления TTL. Ограничения обеспечиваются учётными данными хранилища. При отсутствии действующего разрешения выполняется gRPC-проверка. Положительный ответ кэшируется для пользователя, устройства и действия; отказы не кэшируются. Допускается устаревшее разрешение до истечения TTL, но не использование истёкшего результата при недоступности источника. При отказе кэша выбрана прямая проверка у устройств; ошибка записи разрешения в кэш не блокирует запрос. Если действующего разрешения нет и источник недоступен, операция не разрешается и возвращается временная недоступность. Принят рост нагрузки на источник при отказе кэша. TTL, технология, настройка прав и правила для уже открытого видео/принятых команд пока не согласованы. Кэш авторизации не заменяет проверку сессии, токенов или ограничений выполнения команды. Защита от DDoS этим решением не проектируется. Реализация и измерения задержек отсутствуют.

Для [команд с неизвестным исходом](../docs/to-be-domain-notes.md#восстановление-команд-с-неизвестным-исходом) выбрана автоматическая проверка через адаптер с ручным разбором неразрешённых случаев. Истечение lease исполнителя не снимает сохраняемую в схеме шлюза занятость устройства; следующий экземпляр выясняет результат без слепого повторения действия. Все исполнители учитывают блокировку следующих изменяющих команд, в том числе ручных. Неизвестный исход и последующее уточнение передаются через outbox и очередь результатов команд. Выбрана [возрастающая версия состояния команды](../docs/to-be-domain-notes.md#версия-состояния-команды): шлюз сохраняет состояние, версию и outbox вместе; устройства атомарно проверяют версию и применяют новое состояние, старое событие не откатывает статус. Повторная публикация сохраняет версию и `event_id`. Формат события (снимок или изменение) и обработка разрывов версий ещё не согласованы. Принята возможность временной недоступности удалённого управления отдельным устройством; остальные работают независимо. Процедуры снятия блокировки зависят от существующих протоколов партнёров и должны исключать позднее действие старого запроса. Реализации и проверок сбоев нет.

Для [обратной доставки результатов заданий](../docs/to-be-domain-notes.md#обратная-доставка-результатов-заданий) выбраны отдельные очереди результатов опросов для телеметрии и результатов команд для устройств в RabbitMQ `internal`. Подписки на измерения остаются независимыми. Телеметрия использует отдельный [inbox результатов опросов](../docs/to-be-domain-notes.md#inbox-результатов-опросов): уникальный `event_id`, проверка активного `poll_job_id`, фиксация обработки и обновление задания/занятости/расписания одной транзакцией; ACK после commit. Старое событие не освобождает новый опрос; SQL-блокировка до результата не удерживается. Внешний ключ inbox к заданию и сроки хранения ещё не выбраны. Шлюз публикует через outbox и успехи, и таймауты/ошибки/пропуски. Завершение опроса может обрабатываться раньше записи измерения в историю. Обновлена рабочая схема; реализация ещё предстоит.

Для зависших опросов выбрана [периодическая сверка со шлюзом](../docs/to-be-domain-notes.md#сверка-зависших-опросов-со-шлюзом) через gRPC/TLS со служебным токеном. Фоновый компонент телеметрии проверяет ограниченные порции давно незавершённых заданий по внутреннему адресу логического сервиса; любой экземпляр шлюза может найти сохранённый итог в своей общей схеме. Найденное событие повторно публикуется с прежним `event_id` через outbox и обычную очередь результатов, без нового физического опроса. Отсутствие итога или недоступность шлюза не снимают занятость; проверки повторяются с паузами, длительные неразрешённые случаи требуют сигнала оператору. Интервалы, балансировка и координация самой сверки ещё не определены. Изменены только документация и рабочая схема.

Для [восстановления прерванных опросов](../docs/to-be-domain-notes.md#восстановление-прерванных-опросов) выбран вариант закрытия попытки после истечения lease без повторного физического исполнения старого задания. Шлюз сохраняет начало, исполнителя, версию владения и срок по времени PostgreSQL; условный терминальный переход и outbox фиксируются одной транзакцией. Поздняя запись утратившего право исполнителя отклоняется. Фоновый обработчик шлюза сохраняет прерванный исход, телеметрия получает его через очередь/inbox и после паузы планирует новое задание. Допустимы пропуск измерения и физическое пересечение старого обращения с новым без поддержки контроля на стороне устройства. На изменяющие команды решение не распространяется. Сроки lease, продление, обработка повторной доставки активного задания и детали восстановления ещё требуют реализации; код и проверки сбоев не выполнялись.

Для MVP согласован [один владелец без совместного доступа](../docs/to-be-domain-notes.md#владение-и-доступ-в-mvp): пользователь управляет своими устройствами и сценариями, читает телеметрию и смотрит видео своих устройств. Приглашения и роли членов семьи исключены из объёма MVP. После входа используется [серверная сессия](../docs/to-be-domain-notes.md#пользовательские-сессии) в cookie с Secure, HttpOnly и SameSite, с CSRF-защитой изменяющих запросов и без жёсткой IP-привязки. Состояние принадлежит сервису пользователей в PostgreSQL; Gateway проверяет каждый защищённый запрос через gRPC без кэширования результата в MVP. Приняты дополнительная зависимость от пользователей/БД и риск использования украденной cookie до истечения или отзыва. Первоначальный вход ещё не выбран; реализации нет.

Для передачи пользователя выбран [подписанный внутренний токен](../docs/to-be-domain-notes.md#подписанный-внутренний-контекст-пользователя): сервис пользователей выдаёт его после проверки сессии для конкретного получателя, Gateway передаёт по gRPC/TLS, получатель проверяет подпись и ограничения, затем права на ресурс. Браузер получает только cookie. Формат, алгоритм, TTL, ключи и досрочный отзыв ещё не выбраны. Отзыв сессии не аннулирует уже выданные токены автоматически; фоновые сценарии не должны хранить их для будущих заданий.

Для gRPC-связей во внутренней сети выбраны [служебные токены по направленным парам сервисов](../docs/to-be-domain-notes.md#аутентификация-сервисов-во-внутренней-сети) поверх TLS с проверкой сертификата сервера. Получатель локально проверяет токен и разрешённые методы; единого секрета на систему нет. Конфигурация поступает через окружение, экземпляры не привязаны к IP. mTLS для MVP не выбран. Приняты риск использования украденного токена до замены и необходимость согласованной ротации. Точные правила доступа, ротация и реализация ещё предстоят; решение не заменяет учётные данные PostgreSQL, RabbitMQ или устройств.

Для задания 2 принят единый [пользовательский API Gateway](../docs/to-be-domain-notes.md#вход-пользовательского-приложения), отдельный от шлюза оборудования. Для браузера выбран HTTP/JSON поверх HTTPS, для внутренних вызовов сохраняется gRPC. На границе требуется преобразование запросов и ответов; для собственной реализации Gateway выбраны PHP и Laravel с жизненным циклом приложения на один запрос; конфигурация запуска и точное отображение контрактов ещё не выбраны. Дополнительно принято [требование Twelve-Factor App](../docs/to-be-domain-notes.md#требования-twelve-factor-app) для целевых сервисов: зафиксировано применение всех 12 факторов и открытые вопросы координации экземпляров. Это архитектурные требования; соответствие реализации и поведение при сбоях не проверены.

- Compose содержит незаполненные секции PostgreSQL и `temperature-api`. Для PostgreSQL не настроены требуемый приложением healthcheck, подключение скрипта инициализации и остальные параметры окружения.
- Монолит уже обращается к внешнему API температуры, но отсутствующий сервис не позволяет считать интеграцию готовой.
- Команды запуска в README приложения описывают ожидаемый сценарий; его работоспособность не подтверждена. Команды Go необходимо выполнять из каталога модуля, а не из корня репозитория.
- Автоматические тесты пока отсутствуют; успешную компиляцию нельзя считать проверкой поведения API.
