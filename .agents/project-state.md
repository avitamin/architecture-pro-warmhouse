## Требования задания и открытые решения

Корневой README требует анализ монолита, выделение доменов и контекстов, диаграммы C4 и ER, выбор и документирование API, завершение контейнерного окружения и разработку MVP микросервисов.

Исходное описание компании сохранено в [условиях проекта](../docs/project-brief.md). Условие описывает управление отоплением и опрос датчиков сервером; исходники учебного монолита подтверждают API управления датчиками и HTTP-клиент температуры, но не реализацию команд отопления. При анализе As-Is эти источники следует различать.

Бизнес-цель MVP в условиях перечисляет отопление, освещение, наблюдение и ворота, а задание 6 в README требует сервисы телеметрии и устройств. При планировании MVP нужно сопоставить эти формулировки; выбранная декомпозиция пока не согласована.

Для задания с окружением требуется реализовать `temperature-api` с портом по умолчанию 8081, добавить настройки PostgreSQL и подключить SQL инициализации. Для MVP требуется создать сервисы телеметрии и устройств на разных ООП-языках и интегрировать их с монолитом; брокер сообщений указан как необязательный.

Границы сервисов, технологии новых компонентов, контракты взаимодействия и способ интеграции в рассмотренных документах ещё не зафиксированы как согласованные решения. Их следует обсуждать с пользователем по учебному формату из AGENTS.md. Требования README не означают, что эти компоненты уже реализованы.

Для задания 1 согласованы три области текущего монолита: управление устройствами, управление отоплением и мониторинг температуры. Это логические границы ответственности; изоляция контекстов в коде не реализована: учёт и показания объединены в обработчике, модели и таблице датчиков. Управление отоплением подтверждено условием, но отсутствует в учебном коде.

Ранее обсуждённые области To-Be (устройства с партнёрскими интеграциями, отдельная телеметрия, пользователи, сценарии) и их границы сохранены в [docs/to-be-domain-notes.md](../docs/to-be-domain-notes.md) для задания 2. Они не описывают As-Is. В том числе сохранено решение о принадлежности устройства пользователю в контексте устройств. Окончательное количество микросервисов и контракты ещё не определены.

C4 Context отражает текущую систему по условию: пользователь, монолит и внешние датчики/модули отопления; запросы инициирует сервер. Отличие учебного кода (внешний `temperature-api`, отсутствие команд отопления) явно отмечено в README. БД и внутренние контексты не вынесены на уровень Context.

## Известные ограничения

- Compose содержит незаполненные секции PostgreSQL и `temperature-api`. Для PostgreSQL не настроены требуемый приложением healthcheck, подключение скрипта инициализации и остальные параметры окружения.
- Монолит уже обращается к внешнему API температуры, но отсутствующий сервис не позволяет считать интеграцию готовой.
- Команды запуска в README приложения описывают ожидаемый сценарий; его работоспособность не подтверждена. Команды Go необходимо выполнять из каталога модуля, а не из корня репозитория.
- Автоматические тесты пока отсутствуют; успешную компиляцию нельзя считать проверкой поведения API.
