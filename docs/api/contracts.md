# Правила взаимодействия v1

Этот документ дополняет структурные схемы: JSON Schema и proto3 не выражают права доступа, состояние устройства, сравнение времён и все межполевые ограничения. Такие проверки обязательны на границе соответствующего сервиса. Значения примеров — учебные, не SLA и не подтверждённые настройки оборудования.

## Общие данные и совместимость

- ID — непустая непрозрачная строка из букв ASCII, цифр, `_`, `-`, до 128 символов. Клиент создаёт `command_id` один раз на намерение; UUID подходит, но не обязателен. Идентификаторы команд глобально уникальны в Devices; конфликт чужого ID не раскрывает чужой объект.
- Время — RFC 3339 UTC с `Z`; в protobuf — Timestamp. Длительности политики — положительные целые миллисекунды int32. Отсутствующие необязательные поля не передаются; JSON `null` не используется. Ноль, false и пустое текстовое значение измерения не означают отсутствие Value.
- `acceptance_seq` и `result_version` — положительные десятичные строки до 19 цифр в JSON, uint64 в protobuf. Строки сравниваются численно, не лексикографически. Номер принятия назначает Devices в рамках устройства; версию результата — шлюз в рамках команды. Версия владения исполнителем остаётся внутренним fencing-счётчиком шлюза и не публикуется как версия результата.
- `Value` — конечное число, Boolean или текст. Единица измерения принадлежит определению возможности: для примера температуры используется `Cel`. `Parameters` содержит `operation` и словарь скалярных `arguments`; его допустимую форму определяет `Capability.parameters_schema` (draft-07), а не произвольный JSON от клиента. Devices проверяет управление по текущему каталогу; Scenarios проверяет правило до сохранения. `live_video` не является измеряемой или управляемой возможностью этого среза.
- Пара device/capability во всех запросах и событиях должна обозначать одну зарегистрированную возможность. Вход правила — measurement, выход — control; оба устройства принадлежат владельцу через дома. Сервис возвращает 422 при несовместимых типах, неверном операторе, параметрах или возможности. `lt/lte/gt/gte` разрешены только для чисел; `eq/neq` — для одинаковых типов. NaN/Infinity не допускаются.
- HTTP сохраняет snake_case. Gateway явно преобразует поля; это не слепой ProtoJSON passthrough. Proto Value раскрывается в JSON-скаляр; Rule.configuration разворачивается в верхний уровень. Пустой `next_cursor` proto превращается в отсутствие поля HTTP. Остальные правила — [grpc.md](grpc.md).
- API и package имеют major v1. Удалённые protobuf-номера резервируются при будущем изменении. Consumers игнорируют неизвестные protobuf-поля. JSON v1 использует закрытые схемы: новое поле требует согласованного обновления consumers; несовместимый payload получает новую версию схемы/маршрута. Это осознанное ограничение MVP, не обещание произвольной совместимости.

## Авторизация и ошибки

Gateway на каждом защищённом HTTP-запросе вызывает Users.ValidateSession. Cookie `__Host-warmhouse_session`: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain. Для POST/PUT Users дополнительно проверяет связанный с сессией `X-CSRF-Token`; первоначальная выдача сессии/CSRF относится к внешнему для этого среза входу. Gateway не принимает `user_id` или `source` из тела ручной команды.

Users возвращает подписанный контекст для audience `devices`, `telemetry` или `scenarios`. Получатель проверяет подпись, audience и срок. При пользовательском вызове из Telemetry/Scenarios в Devices сначала выполняется Users.ExchangeContext; прежний токен нельзя просто переслать другому audience. Users проверяет, что исходный audience совпадает с аутентифицированным сервисом, и не продлевает контекст за срок исходной сессии/контекста. Отзыв сессии не обещает немедленно отозвать уже выданный токен. Алгоритм подписи, TTL и управление ключами остаются профилем развёртывания; токен в API — непрозрачная строка, а не выбранный JWT-формат.

Каждый RPC отдельно требует TLS и Bearer-токен направленной пары сервисов. Фоновые методы Scenarios используют только служебную идентичность и сохранённого владельца; токены пользователя/сессии не пишутся в outbox. Положительный кэш разрешений имеет ключ `(user_id, device_id, action)`; Devices — единственный писатель. При промахе или отказе кэша вызывается Devices. Отрицательные ответы не кэшируются. При недоступности источника и отсутствии действующего разрешения — UNAVAILABLE/503, а не PERMISSION_DENIED. SubmitCommand всегда проверяет текущего владельца и допустимость приёма атомарно в Devices, даже если Scenarios ранее получил разрешение из кэша.

| Условие | gRPC | HTTP | Error.code |
| --- | --- | --- | --- |
| Некорректная структура, ID, пагинация, временные границы | INVALID_ARGUMENT | 400 | INVALID_ARGUMENT |
| Нет действительной пользовательской сессии/контекста | UNAUTHENTICATED | 401 | UNAUTHENTICATED |
| Достоверный отказ в праве, CSRF | PERMISSION_DENIED | 403 | PERMISSION_DENIED |
| Объект не найден, ID команды не относится к указанному устройству | NOT_FOUND | 404 | NOT_FOUND |
| Тот же command_id с другим содержимым | ALREADY_EXISTS | 409 | CONFLICT |
| expected_version не совпадает | ABORTED | 409 | CONFLICT |
| Семантически недопустимый запрос или состояние | FAILED_PRECONDITION | 422 | VALIDATION_FAILED |
| Источник прав/конфигурации/БД недоступен | UNAVAILABLE | 503 | UNAVAILABLE |
| Deadline запроса истёк | DEADLINE_EXCEEDED | 504 | DEADLINE_EXCEEDED |
| Неожиданная ошибка | INTERNAL | 500 | INTERNAL |

HTTP Error.code — отдельный закрытый словарь из таблицы, а не буквальное имя gRPC-статуса. HTTP Error содержит `code`, безопасное `message`, `retryable`, `request_id`. Не включать секреты или внутренние исключения. Ошибка служебного токена между Gateway и backend — ошибка инфраструктуры (HTTP 503), а не приглашение пользователю заново войти. `retryable` разрешает повтор при выполнении условий идемпотентности, а не обещает повтор любого POST.

## Чтение и пагинация

История сортируется по `(measured_at DESC, id DESC)`, срабатывания — `(triggered_at DESC, id DESC)`. `limit` по умолчанию 100, максимум 500. Курсор непрозрачен, связан с пользователем, ресурсом, фильтрами и последней парой сортировки; перенос между запросами запрещён. Курсор должен быть защищён от изменения клиентом. `from` включительно, `to` исключительно; при обеих границах требуется `from < to`. Пустая история — 200 с пустым массивом. Последнее известное измерение запрашивается через capability_id и limit=1; время показывает его свежесть, GET не опрашивает прибор.

Это keyset-пагинация живой истории, не транзакционный снимок: поздние измерения могут появиться при повторном обходе. Каждый запрос заново проверяет доступ. ListPollConfigurations использует стабильный порядок device_id/capability_id и cursor; это также не полный снимок реестра. Каждый элемент независимо ограничен valid_until, а удаление/изменение реестра обнаруживается следующими обходами; просроченная локальная копия не допускает новые опросы.

## Конфигурация и сроки

Devices выдаёт снимки только для привязанных доступных measurement-возможностей. `config_version` увеличивается при изменении адресации, адаптера или определения канала. `issued_at < valid_until`; версия — идентичность содержания, обновление срока тем же источником не меняет смысл конфигурации. `endpoint_key` — зарегистрированный непрозрачный ключ, не URL; адаптер разрешает его только через доверенную конфигурацию. Секреты, cookie, пользовательские и служебные токены в снимки не входят. Учётные данные оборудования настраиваются у адаптера отдельно.

Telemetry сохраняет полученную конфигурацию локально, без доступа к таблицам Devices. Для нового опроса:

`expires_at = min(created_at + poll_ttl_ms, config.valid_until)`.

При отсутствии действующего снимка задание не создаётся. Для принятой команды Devices выбирает актуальный снимок control-канала. Запрошенный `expires_at` должен быть в будущем и не позже valid_until; иначе 422, без молчаливого изменения принятого намерения. Шлюз перед началом проверяет срок задания и снимка, совпадение пары device/capability и наличие адаптера. Просроченное до отправки задание получает `expired`, без физического действия. Истечение срока после начала не доказывает прекращения действия; неизвестный результат остаётся unknown.

Явные параметры политики: poll_interval_ms, poll_ttl_ms, срок пригодности снимков, max_data_age_ms, command_ttl_ms, deadlines RPC, пределы повторов/паузы, порог и порция сверки, сроки lease и хранения дедупликации. Точные эксплуатационные значения выбираются по оборудованию и нагрузке. Увеличение срока при повторе того же запроса запрещено. Гарантия дедупликации действует только пока хранится запись ID; клиент после истечения согласованного окна не повторяет старое намерение автоматически.

## Опрос и измерение

1. Планировщик Telemetry в короткой транзакции создаёт poll_job_id, признак активного задания и outbox. На устройство не накапливаются параллельные активные опросы; разные возможности опрашиваются последовательно.
2. Relay публикует PollRequested. Шлюз при повторе использует сохранённое состояние задания; параллельное исполнение одного poll_job_id не запускается. При уже сохранённом результате повторно публикует его с прежним event_id.
3. После адаптера шлюз сохраняет итог и outbox одной транзакцией. При успехе создаются два разных события: MeasurementRecorded и PollCompleted, связанный с measurement_event_id. При timeout/failed/expired/interrupted показание не выдумывается.
4. ACK задания опроса — после сохранения итога. При утрате lease прежняя попытка закрывается как interrupted без автоматического повторного физического исполнения того же задания. Поздняя запись утратившего владение исполнителя отклоняется; допущение возможного физического пересечения старого чтения и новой попытки сохраняется.
5. Telemetry сохраняет измерение идемпотентно по event_id. Событие результата обрабатывает отдельный inbox: event_id, активный poll_job_id, завершение и изменение расписания фиксируются атомарно. Поздний результат старой попытки не освобождает новую.
6. Независимая подписка Scenarios получает то же измерение, не ожидая появления истории. История может сохранить позднее корректное значение; правила используют только более новое measured_at, не старше max_data_age_ms. Для MVP предполагаются корректные часы устройства; недопустимые метки из будущего отвергаются, а не подменяются временем шлюза.

Проверенный контракт адаптера и сопоставление ответа с отправленным заданием являются основанием пары device/capability и типа значения в событии. Consumer не делает gRPC-запрос в Devices на каждое измерение. Равный event_id с другим содержимым — нарушение контракта, не новое измерение.

## Правила и команды

CreateRule присваивает ID, owner_user_id из контекста и version=1. enabled=true устанавливает activated_at и initial_evaluated=false. Для отключённого нового правила activated_at отсутствует. UpdateRule проверяет expected_version под той же блокировкой, что обработчик измерений. Каждое действительное изменение увеличивает version; идентичный PUT с актуальной expected_version возвращает текущую запись без увеличения. Повтор PUT с уже устаревшей expected_version даёт 409; после таймаута клиент читает текущее правило.

Повторное включение, изменение входа, оператора, порога, max_data_age_ms, адресата, параметров действия или command_ttl_ms сбрасывает начальную проверку и прежнее состояние условия. Для активного правила назначается новое activated_at; при изменении условия или действия у отключённого правила activated_at, last_condition_met, last_value и last_measured_at отсутствуют, initial_evaluated=false до следующего включения. Изменение только name сохраняет activated_at и вычисленное состояние. Изменение только enabled с true на false сохраняет прежние activated_at, initial_evaluated и последние значения для диагностики, но запрещает новые срабатывания. При одновременном изменении условия или действия применяется сброс, описанный выше. Команды, уже сохранённые в outbox, не отменяются автоматически.

Событие допускается к версии, активной под блокировкой правила: measured_at строго позже activated_at, строго новее last_measured_at и достаточно свежее. Первое допустимое true создаёт одно действие; после него — только false → true. Состояние, inbox, RuleTrigger и исходящая команда фиксируются вместе. При смене версии между проверкой прав и блокировкой обработка перечитывает правило и повторяет проверку. Повтор ранее зафиксированного события не запускает правило заново; переименование сохраняет last_measured_at, поэтому также не воспроизводит действие.

Срабатывание получает постоянный command_id и срок `triggered_at + command_ttl_ms`. Relay сохраняет их при всех повторах SubmitScenarioCommand. Истёкшую либо окончательно отклонённую команду не заменяет новым ID автоматически. POST создания правила не объявляется идемпотентным: после неоднозначного сбоя его нельзя безусловно повторять; запрос создания не входит в автоматические повторы Gateway.

Devices получает manual/source по SubmitManualCommand и проверенному Gateway; scenario/source — по SubmitScenarioCommand и проверенному Scenarios. Для нового запроса атомарно проверяет владельца, тип/параметры, срок и конфигурацию, фиксирует команду, acceptance_seq и outbox. Для аутентифицированного и авторизованного семантически отклонённого намерения сохраняет rejected и стабильную причину без acceptance_seq/outbox; повтор возвращает прежнюю ошибку. Ошибки структуры/аутентификации и временные ошибки до решения не резервируют ID.

Идемпотентность сравнивает device_id, capability_id, пользователя, источник, нормализованные parameters, expires_at и для scenario — rule_id/version/trigger_id/causation_event_id. Порядок ключей JSON не значим. Идентичный повтор принятого намерения возвращает текущее состояние и replayed=true в gRPC, не новый acceptance_seq. В HTTP повтор выражается кодом 200 вместо 202; тело остаётся Command без поля replayed. Проверка доступа выполняется и при повторе; потерявшему право не выдаётся результат. Отличающийся запрос получает 409 без изменения исходной записи. Ручной источник нельзя подделать полем JSON.

Ручная команда имеет manual_cancel_before_seq = её acceptance_seq: шлюз отменяет только автоматические команды той же возможности с меньшим номером, ещё не зарезервированные к исполнению. Граница отмены сохраняется долговечно и учитывается при позднем приходе старого задания. Резервированная/отправленная команда не прерывается этим механизмом. При unknown последовательность по устройству заблокирована независимо от ручного приоритета.

## Состояние команды и восстановление

| Состояние | Смысл и дальнейшие изменения |
| --- | --- |
| accepted | Devices принял; result_version пока отсутствует |
| queued | Шлюз долговечно сохранил задание; возможны sent, expired, cancelled или failed до отправки |
| sent | Передача предпринята; возможны succeeded, failed или unknown |
| unknown | Исход не доказан; допустимо уточнение в succeeded/failed по доказательству адаптера |
| succeeded | Конкретная операция достоверно завершена; терминальное |
| failed | Достоверная ошибка/отказ; терминальное, требуется гарантия отсутствия позднего действия для разблокировки |
| expired / cancelled | Действие не начиналось; терминальные |
| rejected | Devices не принял; задания шлюзу нет, терминальное |

Шлюз может сразу опубликовать конечный снимок, если промежуточный статус не публиковался. Каждое изменение сохраняет state_changed_at, новый event_id и возрастающий result_version с outbox. Повтор публикации сохраняет все эти значения. Снимок включает status, reason_code и evidence целиком: поля не наследуются из предыдущего события. succeeded требует operation_completed, failed — operation_failed или not_executed, expired/cancelled — not_executed; queued/sent/unknown — none. reason_code — непустой машинный код `[A-Z][A-Z0-9_]*` длиной до 64 символов. Для queued используется QUEUED, для sent — SENT; для остальных исходов это конкретная причина из каталога адаптера (например, COMPLETED, RESPONSE_LOST, DEVICE_TIMEOUT). Потребитель события принимает неизвестный код причины и принимает решения по status/evidence, а не по тексту причины. HTTP-клиент получает status и reason_code; он не определяет доказательство физического исполнения по коду причины. Это открытый словарь, в отличие от HTTP Error.code. Неизвестный исход не трактуется как failed по одному таймауту.

Devices атомарно применяет новую версию. При пропуске версий проверяется достижимость состояния через допустимые промежуточные переходы, а не только соседний переход: accepted → succeeded допустим. Терминальное состояние не меняется на другое; одинаковое терминальное состояние с более новой версией может уточнить reason/evidence без нового действия. Старая версия фиксируется как пропущенная, равная с тем же снимком — повтор, равная с другим снимком — нарушение. Ни одна из них не откатывает статус.

При неизвестном исходе шлюз сохраняет занятость устройства даже после истечения lease. Новый исполнитель выясняет результат по проверенному контракту адаптера, не повторяет действие вслепую. Текущее состояние, совпадающее с желаемым, не является универсальным доказательством выполнения этой команды. Если достоверно разрешить исход нельзя, unknown виден пользователю и требуется ручной разбор; универсального API «снять блокировку» нет.

Telemetry сверяет давно незавершённые задания через GetPollJob. completed разрешает запрос RepublishPollResult: после commit outbox возвращаются прежний event_id и publication_scheduled=true. Ответ не изменяет расписание Telemetry напрямую. pending/running/NOT_FOUND/UNAVAILABLE не снимают занятость; при NOT_FOUND дополнительно проверяется собственный outbox. Повторная публикация не создаёт опрос. Если состояние долго не согласуется, сигнал оператору, без автоматического освобождения.

## Доставка RabbitMQ и граница адаптера

`internal`: durable topic exchanges `wh.jobs.v1` и `wh.events.v1`. Routing keys — type сообщений. Очереди и отправители указаны в AsyncAPI. Измерение доставляется в независимые `wh.telemetry.measurements` и `wh.scenarios.measurements`; экземпляры одного сервиса конкурируют внутри своей очереди. AMQP сообщения persistent, publisher confirms и mandatory routing обязательны. Нероутабельная публикация не считается доставленной. ACK после локального commit; команды шлюз ACK-ает после долговечного приёма, опросы — после итога. Confirm брокера не является ACK потребителя или подтверждением оборудования.

При временной ошибке consumer не ACK-ает незавершённую обработку; повтор с ограниченной паузой, без горячего requeue-цикла. Невалидная схема, неизвестная schema_version, невозможный переход или одинаковая версия с другим снимком сохраняются в долговечный карантин обработки вместе с причиной, затем ACK; при неудаче записи ACK нет. Каждому потребителю принадлежит собственный карантин, сигнал оператору и ручная процедура возврата после устранения причины. Число попыток и хранилище карантина — настройки реализации; нельзя молча отбросить сообщение.

Адаптер получает poll_job_id/command_id, снимок, срок и (для команды) параметры. Он переводит их в существующий протокол партнёра, используя MQTT 5/TLS через vhost devices. Ответ должен коррелироваться с конкретным запросом, устройством и каналом; сырые данные проходят проверку до внутренних событий. Адаптер возвращает измерение с фактическим measured_at либо ошибку; для команды — подтверждение конкретной операции, достоверный отказ или неизвестность. Таймаут ожидания не отменяет отправленную операцию.

Точные MQTT topics/payloads, поддержка operation ID, отмены и защиты от повторов зависят от производителя. Этот контракт не вводит новые требования к прошивке без проверки. Конкретные интеграции и их физическое поведение здесь NOT RUN.
