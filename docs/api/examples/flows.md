# Сквозные примеры и критерии приёмки

JSON примеры находятся в [fixtures.json](fixtures.json), HTTP — в именованных examples [OpenAPI](../openapi.yaml), события — в [messages.yaml](../asyncapi/messages.yaml). Идентификаторы одного намерения совпадают между транспортами. Пример CommandStateChanged.unknown относится к отдельному cmd-auto-unknown-1; таблица отказов ниже содержит независимые варианты, а не одну хронологию успешной команды. Время 2026-10-21 и интервалы — иллюстрация, не действующие настройки. Таблицы ниже задают ожидаемое поведение будущих сервисов; это не протокол выполненных runtime-тестов.

## Опрос и автоматическое включение

Предусловия: user-1 владеет house-home и dev-thermostat; измерение cap-temperature имеет type=number, unit=Cel, cap-heating принимает `{"operation":"set","arguments":{"enabled":true}}`. Правило rule-heat активно с 10:00:00Z, version=1: температура lt 18, max_data_age_ms=60000, command_ttl_ms=30000.

| Шаг | Контракт | Проверяемая связь |
| --- | --- | --- |
| 1 | ListPollConfigurations | Снимок версии 1 пригоден до 10:05:00Z |
| 2 | PollRequested | poll-1, evt-poll-request-1, срок 10:00:10Z; совпадают device/capability снимка |
| 3 | Адаптер | 17 °C измерено в 10:00:01Z, получено шлюзом в 10:00:02Z |
| 4 | MeasurementRecorded и PollCompleted | Разные event_id; PollCompleted.measurement_event_id = evt-measurement-1 |
| 5 | Telemetry | История с event_id=evt-measurement-1; результат снимает занятость только poll-1 |
| 6 | Scenarios | Первое свежее true создаёт trigger-1 и постоянный cmd-auto-1 |
| 7 | SubmitScenarioCommand | Служебный caller Scenarios; owner=user-1; rule/trigger/event совпадают со срабатыванием |
| 8 | CommandRequested | cmd-auto-1, acceptance_seq=40, source=scenario, expires_at=10:00:33Z |
| 9 | CommandStateChanged | Подтверждено конкретное выполнение, status=succeeded, result_version=3 |
| 10 | GET history / triggers / command | История и результат читаются независимо; trigger уже может быть виден до приёма cmd-auto-1 Devices |

В fixtures событие command.requested должно происходить после trigger.triggered_at, а результат — после отправки. Промежуточные версии результата 1 и 2 могут не прийти: версия 3 является полным снимком. Это не гарантия exactly-once физического исполнения.

## Ручная команда

```http
POST /api/v1/devices/dev-thermostat/commands
Content-Type: application/json
Cookie: __Host-warmhouse_session=<session>
X-CSRF-Token: <csrf>

{"command_id":"cmd-manual-1","capability_id":"cap-heating","parameters":{"operation":"set","arguments":{"enabled":true}},"expires_at":"2026-10-21T10:00:30Z"}
```

202 содержит Command со status=accepted, acceptance_seq=41 и Location `/api/v1/devices/dev-thermostat/commands/cmd-manual-1`. Gateway получил user-1 через Users, а Devices назначил manual по разрешённому RPC. Идентичный повтор возвращает 200 и текущее состояние; число заданий и acceptance_seq не меняются. Тот же ID с enabled=false или другим expires_at даёт 409. Ручная команда отменяет лишь старые ожидающие автоматические команды cap-heating; выполняемая команда и unknown не обходятся.

## Ошибки и перестановки

| Сценарий | Ожидаемый результат и граница проверки |
| --- | --- |
| Опрос timeout | PollCompleted.outcome=timeout без measurement_event_id; MeasurementRecorded отсутствует |
| Успешный результат раньше истории | Расписание обновляется; история появляется позже, это допустимо |
| Повтор poll result после commit до ACK | Inbox не меняет расписание второй раз |
| Старый poll result после старта нового задания | Не освобождает новое poll_job_id |
| Сверка completed | RepublishPollResult сохраняет прежний event_id; физический опрос не выполняется |
| Сверка pending/running/NOT_FOUND/недоступность | Занятость сохраняется; NOT_FOUND требует проверки собственного outbox |
| Повтор события измерения | История одна; каждое правило учитывает event_id один раз |
| Новое 17 °C после уже обработанного 17 °C | Условие остаётся true, новое срабатывание не создаётся |
| Первое 17 °C после активации | Одно срабатывание; первое 19 °C только фиксирует false |
| measured_at до активации или старее last_measured_at | Действия нет; поздняя корректная история допустима |
| Превышен max_data_age_ms | Нового действия нет, прежнее состояние условия сохраняется |
| Отключение → включение | Новая версия/activated_at; первое свежее true после включения снова вызывает действие |
| Только переименование | Версия меняется, activated_at и last_measured_at сохраняются; повторного действия нет |
| Конкурентный PUT со старой expected_version | 409; чужое изменение не перезаписано |
| Отключение при уже сохранённом outbox | Новых срабатываний нет; ранее созданная команда остаётся |
| Истёкшая конфигурация до планирования | PollRequested не создаётся |
| Срок задания истёк в очереди | expired без физического действия |
| Отказ источника прав и промах кэша | 503, действие не разрешено; это не 403 |
| Чужое устройство или подмена owner/source | Запрос отклонён; браузерные поля не определяют служебный контекст |
| Потерян ответ Submit после commit | Повтор с прежним ID возвращает сохранённую команду |
| Результат v3 succeeded, затем v2 unknown | Статус остаётся succeeded |
| Новая v5 после v2 unknown | Применяется самодостаточный допустимый снимок без ожидания v3/v4 |
| Та же версия, другой status/evidence | Нарушение контракта, карантин, без перезаписи |
| Таймаут физической команды | unknown, устройство занято; безусловного повтора и ручного обхода нет |
| Адаптер видит желаемое состояние, но не доказывает конкретную операцию | unknown сохраняется |
| Lease исполнителя истёк | Старая запись результата отклоняется; для команды это не разрешение повторного действия |

## Что проверяется автоматически

Валидаторы проверяют структуру спецификаций, ссылки, positive/negative payload-примеры, общие поля proto/JSON, связность идентификаторов и времён fixtures. Отрицательные примеры охватывают неверный тип значения, обязательный ID, незаконный статус, подмену source, неполный снимок и результат опроса без корректной связи на измерение.

Транзакции, конкуренция, ACK, повторная доставка, права и реальные MQTT-операции здесь не запускаются. После реализации таблица станет основой интеграционных и fault-injection проверок. До этого их статус — **NOT RUN**.
